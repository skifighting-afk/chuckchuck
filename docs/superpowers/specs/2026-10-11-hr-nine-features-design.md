# 척척사장 HR 추가 기능 9개 설계

상태: 2026-10-11 사용자 ‘이 설계 승인’ 확인. 직접 구현 계획 승인. 기능 구현·서버 검증 완료, 전체 리뷰·CI·운영 배포 확인 진행 중.
작성일: 2026-10-11
선택 범위: 이전 추천 목록의 1·3·4·5·6·7·8·9·10번.

## 목적과 범위

소규모 매장 사장님과 직원이 채용, 첫 근무, 교육, 근무 배정, 소통, 퇴사 준비를 같은 기록으로 이어 간다. 기존 근태·급여·근로계약서·매뉴얼에 연결하며 매출, 지출, 순이익, 재고, 발주는 이번 개발 범위에 포함하지 않는다. 직원 추천 채용(이전 목록 2번)은 선택되지 않았다.

성공 기준은 기능 수가 아니라 다음 세 가지다. 사장님은 반복 입력과 뒤늦은 확인을 줄이고, 직원은 본인에게 필요한 업무와 처리 상태를 알며, 매장과 개인별 조회·수정 권한이 서버에서 지켜진다.

## 확인한 기존 구조와 결정

- React/TypeScript 앱과 기존 서버 API, Supabase/PostgreSQL 마이그레이션 경로를 사용한다. 새로운 별도 서비스는 만들지 않는다.
- 직원 관리의 `extra.skills`, 평가 메모·칭찬, 주 최대 근무 시간, 직원 상태를 연결한다.
- 근무표 도우미에 주간 시간과 월간 주말 횟수가 있다. 희망 근무량과 주말·마감·연속 근무 비교를 이 흐름에 추가한다.
- 매뉴얼·교육 진행을 신입 담당자 및 숙련도 확인에 연결한다.
- 기존 1:1 메시지와 익명 건의함은 있다. 담당자·처리 상태가 있는 상담과 정기 면담을 별도 용도로 설계하며, 기존 익명 기록을 실명 상담에 연결하지 않는다.
- 지원자·면담 비공개 메모·상담·만족도 응답은 일반 `Team` 응답에 넣지 않는다. 별도 HR 테이블 및 API에서 접근 범위에 맞춰 응답한다.
- 기존 작업 폴더에 미완성 직원당 요금·시작 안내 변경이 있다. 이 설계는 그 변경을 출시 승인하거나 이번 범위에 포함하지 않는다. 구현 시작 시 별도 변경으로 보존하고 기준 브랜치를 분리한다.

## 접근 방식

세 가지 방식을 비교했다. 독립 HR 앱은 로그인과 직원 데이터가 중복된다. 모든 기능을 기존 직원 정보 JSON에 추가하면 비공개 자료가 광범위한 응답·가져오기·내보내기에 섞일 위험이 있다. 권장 방식은 기존 앱 안에 HR 화면을 붙이고, 민감 기록은 별도 저장·권한 계층으로 관리하는 것이다.

사장님은 직원 관리에서 ‘채용’, ‘성장·면담’, ‘지급·반납’을 연다. 근무 스케줄에는 ‘희망 근무량’과 ‘배정 균형’을 추가한다. 직원 홈에는 ‘내 교육’, ‘근무 희망’, ‘의견·상담’, ‘받은 물품’을 작업 카드로 보여 준다. 모든 기능을 홈에 펼쳐 놓지 않는다. 현재 선택한 매장을 제목에 항상 표시한다.

## 1. 채용 지원자 관리 (HR-01)

사장님이 지원자 이름, 연락처, 희망 매장·업무, 가능한 시간, 지원 경로를 직접 등록한다. 이번 첫 버전은 구인 플랫폼 수집·외부 공개 지원 폼·문자 자동 발송을 포함하지 않는다.

흐름: 지원 접수 → 면접 예정 → 면접 완료 → 채용 결정 → 직원 등록. 보류·지원 철회·종료는 별도 상태다. 면접 일정과 확인할 질문을 기록하고, 채용 결정은 사람이 한다. 자동 점수·자동 탈락은 제공하지 않는다.

‘직원으로 등록’은 사장님이 대상 매장·이름·연락처·업무를 확인한 뒤 실행한다. 기존 직원 후보가 있으면 연결 여부를 선택하며 전화번호만 같다는 이유로 자동 합치지 않는다. 등록 후 상태는 ‘입사 준비’이며, 임금·계약·계정 연결은 기존 흐름에서 따로 확인한다. 같은 지원자를 두 번 눌러도 직원이 중복 생성되지 않아야 한다.

완료 기준: 모바일에서 지원자 등록, 면접 일정 수정, 상태 이동, 기존 직원 연결 또는 신규 직원 등록을 완료한다. 다른 사업자·허용되지 않은 지점 지원자는 조회·수정할 수 없다. 종료된 지원자의 개인정보 보관 기간을 설정하고 정리 대상을 확인할 수 있다. 구체적인 기간은 서비스 보관 정책에 맞춰 화면에 명시한다.

## 3. 신입 담당 선배 배정 (HR-03)

사장님이 신입, 담당 선배, 시작일·종료일, 교육할 업무와 관련 매뉴얼을 정한다. 선배는 본인에게 배정된 교육만 보고 단계별 진행 메모를 남긴다. 신입은 담당자 이름, 교육 목록, 질문할 위치를 확인한다. 급여·개인 평가·상담 기록은 선배에게 공개하지 않는다.

흐름: 담당자 배정 → 첫 근무 안내 → 교육 진행 → 신입 확인 → 담당자 완료 확인. 배정 변경 시 이전 진행 기록과 변경 이력이 유지된다. 퇴사·전근한 선배는 새 진행 기록을 남길 수 없고 사장님에게 재배정 안내를 보여 준다.

완료 기준: 새 담당자가 미완료 교육을 이어받을 수 있다. 교육 완료만으로 독립 근무 가능 또는 임금 변경이 자동 확정되지 않는다.

## 4. 업무별 숙련도 관리 (HR-04)

매장 업무 목록을 만들고 직원별로 ‘교육 전 / 교육 중 / 도움받으면 가능 / 혼자 가능’을 표시한다. 직원은 본인 현황과 다음 학습 항목을 본다. 담당자는 확인한 업무·일자·근거 매뉴얼·짧은 메모를 남긴다. 현재 자유 입력식 ‘가능 업무’는 원문을 보존하며 확인되지 않은 태그를 숙련 인증으로 자동 전환하지 않는다.

사장님과 위임받은 교육 담당자가 확인 상태를 변경한다. 근무 편성에서 필요한 업무가 미확인일 때 안내하되 자동 탈락·급여 변경·징계 처리를 하지 않는다. 직원은 재확인을 요청할 수 있다.

완료 기준: 한 업무의 교육→확인→변경 이력을 추적한다. 권한 없는 직원이 자신을 ‘혼자 가능’으로 확정할 수 없다. 이전 업무 태그와 기존 근무표가 유지된다.

## 5. 희망 근무량 맞추기 (HR-05)

직원이 적용 기간과 주·월 기준을 선택해 희망 근무일 수 또는 시간의 범위를 입력한다. 가능한 시간·휴무 희망·최대 근무 시간과 구별해 저장한다. 변경 전후를 사장님에게 보여 주고, 반영 여부를 직원도 확인한다.

편성 화면에는 ‘희망 60시간 / 배정 48시간 / 차이 -12시간’처럼 표시한다. 희망량은 고용계약의 보장 시간이나 자동 배정 약속으로 표현하지 않는다. 근무 시간은 기존 휴게·자정 넘김·주 시작일 계산 함수를 재사용한다. 희망이 미입력인 직원은 0시간으로 간주하지 않는다.

완료 기준: 희망 기간 경계, 주·월 단위, 휴게 시간, 야간을 넘는 근무를 정확히 계산한다. 직원 A가 직원 B의 희망을 고치거나 조회할 수 없다. 자동으로 근무표를 수정·공개하지 않는다.

## 6. 근무 배정 균형 확인 (HR-06)

선택한 기간의 배정 시간·주말 근무·마감 근무·연속 근무일을 직원별로 나란히 보여 준다. 희망량·가능 시간·담당 업무와 함께 확인하여 서로 조건이 다른 직원을 단순 순위로 비교하지 않는다.

‘균형 확인’은 근무 배정을 검토하는 자료이며 직원 평가 점수 또는 차별 판단 점수가 아니다. 지표를 누르면 근거 근무 목록을 연다. 마감 기준을 설정하지 않은 매장은 ‘기준 설정 필요’로 표시한다. 일정 변경은 기존 편집→미리보기→공개 흐름을 사용한다.

완료 기준: 야간 근무의 중복 날짜 집계, 지점 지원 근무, 휴가·휴무, 월 경계를 검증한다. 직원에게는 본인 배정만 보여 주며 다른 직원의 비공개 희망량·상담 자료를 노출하지 않는다.

## 7. 정기 면담과 약속 관리 (HR-07)

면담 대상·담당자·예정일·주제, 직원과 공유할 요약, 담당자 비공개 메모를 구분한다. 약속은 ‘무엇을 / 누가 / 언제까지’로 기록한다. 직원은 공유된 요약과 본인 할 일을 확인하고 의견을 남긴다.

흐름: 일정 등록 → 면담 진행 → 공유 내용 확인 → 약속 진행 → 완료·기한 변경. 비공개 메모는 명시된 담당자와 사장님만 보고 직원용 응답·푸시·일반 내보내기에 들어가지 않는다. 공유 여부를 바꿀 때 공개 대상을 미리 보여 준다.

완료 기준: 담당자 변경, 기한 연장, 직원 확인, 완료 이력이 남는다. 면담에 적은 ‘다음 달 근무 변경’이 실제 근무표·계약·급여를 자동 수정하지 않는다.

## 8. 직원 의견·상담 창구 (HR-08)

직원이 받는 사람과 공개 범위를 확인하고 의견·상담을 접수한다. 사장님이 명시적으로 위임한 상담 담당자만 선택할 수 있다. 이번 기능은 처리 담당자에게 작성자가 보이는 상담이다. 기존 익명 건의함은 별도 경로로 유지하고 두 경로의 표시를 분명히 한다.

흐름: 접수 → 담당자 확인 → 답변·추가 확인 → 처리 완료 → 직원 재문의. 담당자가 퇴사하거나 권한이 회수되면 사장님에게 인계 대기 상태로 표시하고 새 담당자가 정해지기 전 접근을 차단한다. 직원 본인과 지정 담당자·사장님 외에는 본문을 볼 수 없다. 사장님이 접근 가능한 서비스 구조임을 제출 전에 명시한다.

완료 기준: 같은 매장의 동료도 타인의 접수를 볼 수 없다. 푸시는 ‘상담 답변이 도착했어요’처럼 제목·접속 링크만 전하며 상담 본문을 담지 않는다. 답변·담당자 변경의 이력과 중복 접수 방지가 작동한다.

## 9. 짧은 근무 만족도 확인 (HR-09)

사장님이 업무량·교육·소통 관련 짧은 설문과 기간을 정한다. 직원은 자발적으로 응답하며 건너뛰거나 종료 전 수정할 수 있다. 제출 전 ‘응답은 사장님과 지정 담당자에게 이름과 함께 보입니다’를 명확하게 보여 준다. 익명 보장·자동 퇴사 위험 점수·직원별 순위는 제공하지 않는다.

결과는 응답 인원 / 대상 인원, 항목별 분포, 직원이 직접 적은 의견을 보여 준다. 미응답을 불만 또는 낮은 점수로 계산하지 않는다. 소규모 결과의 과도한 해석을 막기 위해 응답 수를 항상 함께 표시한다. 면담은 사장님이 판단해 별도로 등록한다.

완료 기준: 한 직원당 한 설문 한 응답, 기간 종료 처리, 제출 전 공개 범위 안내, 본인 응답 수정, 권한별 결과 조회가 검증된다. 기존 익명 건의 데이터를 실명 설문에 결합하지 않는다.

## 10. 유니폼·출입키 지급·반납 (HR-10)

물품명·수량·지급일·지급 담당자·반납 예정일·선택 메모를 직원에게 연결한다. 금액·구매·재고 수불은 다루지 않는 HR 지급품 기록이다. 물리적 출입키의 번호 표시는 별칭만 받고 비밀번호·출입코드 입력을 요구하지 않는다.

흐름: 지급 기록 → 직원 수령 확인 → 반납 요청 → 담당자 반납 확인. 부분 반납과 분실은 사유가 있는 별도 상태다. 퇴사 준비 화면에 미반납 목록을 연결한다. 물품 미반납이 급여 자동 차감이나 퇴사 차단으로 이어지지 않는다.

완료 기준: 2개 중 1개 반납, 중복 반납, 담당자 변경, 퇴사 직원의 조회·담당자 기록 권한을 검증한다. 받은 물품과 직원 확인 내역이 양쪽에서 동일하게 보인다.

## 데이터와 API 경계

제안 테이블: `hr_candidates`, `hr_buddy_assignments`, `hr_skill_definitions`, `hr_skill_records`, `hr_work_preferences`, `hr_meetings`, `hr_meeting_actions`, `hr_cases`, `hr_case_messages`, `hr_pulse_campaigns`, `hr_pulse_answers`, `hr_item_assignments`, `hr_item_events`, `hr_grants`, `hr_audit`. 배정 균형은 기존 근무표에서 계산하고 결과를 별도 정답 데이터로 저장하지 않는다.

모든 기록은 owner와 branch_id, 생성·수정 시각, 버전, 작성자 식별자를 갖는다. 대상 직원·담당자는 현재 연결된 매장의 기존 식별자를 참조한다. HR 권한은 기존 근태·급여 권한과 독립적으로 위임하며 위임자·지점·영역·만료일을 기록한다. 민감 기록의 담당자 식별자는 현재 권한 검증을 대신하지 않는다.

서버는 기존 `resolveStore`를 사용하고 모든 조회·변경에서 사업자, 지점, 재직/입사 준비 상태, 기능 권한, 본인 여부를 검증한다. 클라이언트가 보낸 owner·employeeId를 권한 근거로 믿지 않는다. 직접 DB 클라이언트 접근은 RLS로 차단하고 기존 서버 어댑터를 사용한다.

HR API는 `/api/hr/...` 아래 조회·변경을 분리한다. 요청은 스키마 검증·길이 및 건수 제한·Origin 검사·서비스 이용 상태를 적용한다. 변경에는 version을 사용하고 충돌은 409로 안내한다. 채용 전환·지급·반납·설문 제출은 고유 요청 키와 제약으로 중복 처리되지 않는다. 기존 이용 요금 계산은 이번 작업에서 변경하지 않는다.

기록의 보관·삭제·계정 탈퇴·직원 익명화는 기존 서비스 보관 정책과 연결한다. 개인정보 정책에 근거 없이 새로운 보관 기간을 단정하지 않는다. 일반 감사에는 변경 종류·기록 식별자·담당자 변경만 남기고 상담 본문·비공개 메모·설문 답변은 넣지 않는다. 실패한 저장을 완료로 표시하지 않는다. 알림 실패는 저장 상태와 구분한다.

## 화면과 모바일

기존 짙은 초록·밝은 배경·연두 강조를 이어 간다. 일반 상태는 색만으로 구분하지 않고 문구와 아이콘을 함께 쓴다. 360·390·768·1280px에서 핵심 등록·수정·확인 흐름을 점검한다. 모바일 채용 단계는 가로 드래그를 강제하지 않고 상태별 목록과 명시적 이동 버튼으로 제공한다.

입력 오류는 해당 항목 옆에서 설명하고 값은 보존한다. 제출 중 중복 클릭을 막고 저장 결과를 보여 준다. 빈 화면에는 다음 한 가지 행동을 안내한다. 접었다 펴는 구역, 키보드 이동, 포커스 복귀, 큰 글씨, 스크린리더 이름을 확인한다. 교육과 일정의 상태 변화는 짧게 보여 주고 HR 본문에 장식용 3D나 자동 재생을 넣지 않는다.

## 구현 순서와 완료 판정

1. 공통 HR 권한·저장 계층과 권한 테스트를 먼저 만든다.
2. 채용(HR-01), 신입 담당자(HR-03), 숙련도(HR-04)를 기존 직원·매뉴얼에 연결한다.
3. 희망 근무량(HR-05)과 배정 균형(HR-06)을 근무표에 연결한다.
4. 면담(HR-07), 상담(HR-08), 만족도(HR-09)를 제한된 조회·알림과 함께 만든다.
5. 지급·반납(HR-10)을 직원·퇴사 준비에 연결한다.
6. 아홉 기능의 예시 데이터와 역할 전환 가능한 데모를 제공하고, 모바일·기존 근태/급여 회귀를 검증한다.

단계별 완료는 실제 서버 저장→재조회, 두 계정 간 격리, 다른 사업자·지점 접근 거부, 권한 회수, 동시 저장·중복 요청, 모바일 조작을 모두 확인한 뒤 판단한다. 데모는 예시 데이터임을 표시하고 실제 계정 데이터와 섞지 않는다. 자동화 시험만으로 배포 성공을 선언하지 않으며, 실제 배포 후 화면과 API를 확인한다.

이 설계는 승인되었으며 아직 앱 동작을 바꾸지 않았다. 작성한 구현 계획을 검토하고 실행 방식을 정한 다음 개발한다.
