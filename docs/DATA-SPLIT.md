# 가게 데이터 나누기 계획 (작업 081)

지금 가게 하나의 거의 모든 정보가 `stores.data` JSON 한 덩어리에 있다. 저장할 때마다 덩어리 전체를 다시 쓰고,
여러 사람이 동시에 고치면 버전 충돌(409)이 난다. 기록이 많은 칸부터 한 단계씩 테이블로 옮긴다.
각 단계는 되돌릴 수 있게 하고, 단계마다 E2E·서버 테스트를 통과해야 다음으로 간다.

| 순서 | 칸 | 상태 | 방법 |
|---|---|---|---|
| 0 | 출퇴근(attendance) | 완료(작업 045) | `attendance_records`가 원본. 최근 기간만 JSON에 붙여 화면에 보내고, 저장 때 트리거가 테이블로 옮긴다. |
| 1 | 근무표(shifts) — 그림자 복사 | **완료(이번 단계)** | `shift_records`에 저장할 때마다 같게 복사(원본은 아직 JSON). `shift_mirror_drift(owner)`로 차이 0 확인. 대표 변경·탈퇴 삭제도 함께 처리. |
| 2 | 근무표 — 읽기 전환 | 다음 | 서버가 `shift_records`에서 보려는 주(週) 앞뒤만 읽어 붙이고, 저장은 출퇴근처럼 트리거로. 운영에서 1주일 동안 차이 0을 확인한 뒤 진행. |
| 3 | 근무표 — JSON에서 빼기 | 그다음 | `_shiftsFrom` 표시로 범위 밖 기록은 건드리지 않게(출퇴근과 같은 방식). |
| 4 | 직원(employees) | 이후 | 직원 한 명 = 한 행. 계약·급여가 직원 정보에 묶여 있어 마지막에. 개인정보 칸 암호화도 이때 검토. |
| 5 | 휴가·공지·대타(_operations) | 이후 | 신청 한 건 = 한 행. 직원이 동시에 신청해도 충돌하지 않게. |

확인 방법(1단계): `select owner, shift_mirror_drift(owner) from stores where shift_mirror_drift(owner) <> 0;` 결과가 비어 있어야 한다.
되돌리기(1단계): 마이그레이션 파일 맨 위 주석의 drop 문 실행 — 원본이 JSON이라 데이터 손실 없음.
